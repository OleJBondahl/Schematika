## Authoritative guidance

This wave applies the global `python-coding-and-tooling` skill's "Docstrings" section and `reviewing-ai-generated-python` skill's smell #4 ("Misleading / inflated docstrings"). Read both before starting.

Summary of the rule:

> Default: don't write a docstring. Identifier names + type hints already say WHAT. Reserve docstrings for non-obvious WHY: invariants, edge cases, units, side-effect ordering, hidden constraints. When you do write one, it's a single line.

## Decision rule per multi-line docstring

For each multi-line docstring:

1. **Read the first line + skim the rest.** Is there a non-obvious WHY anywhere in it (an invariant, an edge case, a unit, a side-effect order, a coupling with another module that isn't visible from the call site)?
   - **No** (it just paraphrases the signature with `Args:` / `Returns:` / `Raises:` blocks): **DELETE** the multi-line body, keep only the first line if it adds anything beyond the function name. If the first line is also just `"""Add a terminal to the circuit."""` for `def add_terminal`, **delete the docstring entirely** if ruff allows (private functions only — ruff D requires docstrings on public/module/class).
   - **Yes**: **KEEP only the WHY line(s)**. Delete the `Args:` block. Delete the `Returns:` block (the type annotation says it). Delete the `Examples:` block (write a real test instead).

2. **Constraints from ruff `D`:**
   - Modules (D100), classes (D101), public methods (D102), `__init__` (D107), magic methods (D105) need at least *some* docstring. Shrink to one line.
   - Private functions (D103 doesn't apply to underscore-prefixed names): docstring is optional — delete entirely if redundant.

3. **`Raises:` exceptions** — keep ONLY when (a) the exception is part of the public contract AND (b) it's not obvious from the function name. E.g. a `build()` method that can raise `PCBBuildError` is worth a one-line `"""...Raises PCBBuildError if ..."""`.

## Examples

```python
# ❌ AI-bloat — delete or shrink to 1 line
def add_terminal(self, tm_id: str, *, poles: int = 1) -> Terminal:
    """Add a terminal to the circuit.

    Args:
        tm_id: The terminal identifier.
        poles: The number of poles. Defaults to 1.

    Returns:
        The newly created terminal.
    """

# ✅ Shrink — name + type hints carry the rest
def add_terminal(self, tm_id: str, *, poles: int = 1) -> Terminal:
    """Auto-connects to the previous component in the chain unless `connect_from_previous=False`."""

# ✅ Or, if the WHY is the function's invariant:
def _resolve_pin(...) -> str:
    """Returns the canonical pin id; left/right pole indices map to "11"/"12"/"14" per IEC."""
```

## Out of scope

- Adding new docstrings where they're missing — Wave R4 already covered presence; Q1 only shrinks.
- Touching test files (per-file-ignored for D anyway).
- Improving non-docstring comments inline in code — separate concern.
- Refactoring the underlying functions.

## Risk

- Deleting a docstring that documents a non-obvious WHY because the reviewer skimmed too fast. Mitigation: when in doubt, **keep the WHY line, delete the rest**.
- Removing a `Raises:` block that documented a real domain exception. Mitigation: ty's typed exception hierarchy + the `reviewing-ai-generated-python` smell #11 ("inconsistent error handling") catches misalignment; one-line `Raises:` is allowed for public boundary methods.
- A test snapshot or doctest that depends on docstring text. Mitigation: pytest must remain at 1827; if a test breaks, restore that one docstring.
