# Wave L1 baseline — Pre-commit hardening

Branch base: `branch1` @ `f1d1817` (post-Q3 + shim safety).

This wave makes every gate in `.pre-commit-config.yaml` honest about whether it blocks commits or is informational.

## State at start

`.pre-commit-config.yaml` has 8 hooks:

| Hook | Current label | Actually fails? | Strict scope |
|---|---|---|---|
| `ruff-format` | (no label) | Yes | per-file diff |
| `ruff-check` | (no label) | Yes (with `--fix`) | per-file diff |
| `ty-check` | (no label) | Yes | per-file diff |
| `vulture` | (dead code, strict) | Yes (whole `src/`) | already strict — Q3 |
| `import-linter` | (layering contracts) | Yes | whole repo |
| `codesight-wiki` | (AST wiki, advisory) | No (informational) | whole repo |
| `fp-purity-gate` | (advisory) | **No — labeled advisory but exits 1 on violations**; misleading | whole repo |
| `api-style-gate` | (advisory) | **No — runs without `--strict`, always exits 0**; misleading | whole repo |

Verified states on `branch1` head (`f1d1817`):
- `uv run pre-commit run --all-files` → all hooks pass
- `uv run python scripts/api_style_gate.py --strict` → exits 0
- `uv run python scripts/fp_purity_gate.py` → exits 0
- `uv run lint-imports` → 2 contracts kept, 0 broken
- `uv run vulture src --min-confidence 80` → exits 0

Pre-existing import-linter / failing-test concerns documented in `docs/TOOLING.md` are stale and resolved.

## Plan

1. **Drop misleading "advisory" labels** on hooks that already fail or could fail:
   - `fp-purity-gate` → label "(strict)"; the script exits 1 on violations.
   - `api-style-gate` → wire `--strict` flag into the entry; label "(strict)".
2. **Keep `codesight-wiki` advisory** — it's informational regen, not a gate. Label remains "(AST wiki, advisory)".
3. **Audit `pass_filenames` per hook** — already done in Q3 for vulture. Other hooks (`ruff-*`, `ty-check`) keep per-file scope (fast incremental checking).
4. **Update `docs/TOOLING.md`**:
   - Drop the "Two failing tests" and "import-linter pre-existing failures" sections (resolved).
   - Drop the "Pre-commit hooks were added with `--no-verify`" notice — clean now.
5. **Verify**: a fresh `uv run pre-commit run --all-files` exits 0; a deliberately introduced violation in each rule category gets blocked.

## Done condition

- `.pre-commit-config.yaml` has no "advisory" hooks except `codesight-wiki` (which is information-only).
- `api_style_gate.py` is invoked with `--strict` in pre-commit.
- `uv run pre-commit run --all-files` exits 0.
- A test-only commit that introduces a `fp-purity` violation, an `api-style` violation, or a `vulture` finding is blocked by pre-commit. (Verified manually, not stored as a regression test.)
- `docs/TOOLING.md` no longer carries stale notes about pre-existing failures or `--no-verify` workarounds.
- `uv run pytest -q --continue-on-collection-errors` ≥ 1981.
- `uv run ty check` 0, `uv run ruff check src tests` ≤ 90, `uv run vulture src --min-confidence 80` 0.

## Out of scope

- L2's job: making `just ci` the canonical local-CI command (run all tools + tests except mutmut).
- L3's job: numeric ratchet enforcement script (lock current counts as regression baselines).
- New hooks (e.g. `pytest --collect-only`) — not adding now; the existing set is enough once labels are honest.
- `pre-commit autoupdate` — these are local hooks, not pinned versions; not applicable.

## Risk

- A hook that currently passes flips to "strict" but actually has a latent failure mode under different inputs. Mitigation: `pre-commit run --all-files` is the canonical end-state check; if it passes, the strict label is honest.
- Removing the "advisory" label on a script that genuinely should be advisory. Mitigation: kept `codesight-wiki` advisory; only removed the label on hooks whose scripts already exit 1 on violations or accept `--strict`.
